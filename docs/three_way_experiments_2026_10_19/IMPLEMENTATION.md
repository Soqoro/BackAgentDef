# Implemented three-way preparation

The runnable entry point is `seek_three_way.py`. It imports the additive
`seek/three_way/` package and does not change the existing Stage I or Seek launchers.
The source handoff files retain their uploaded `(1)` names.

| Module | Implemented path |
|---|---|
| core.py | Existing seals, immutable artifacts, source binding, split lineage/exposure validation, asset inventory and phase approval checks |
| training.py | Private seeded cue manifest, aligned native FastChat C/LQ/LO compiler, optional semantic-query replication, native token-label preflight, pairwise match checks, common full-tuning command |
| spans.py | Public offsets/content hashes, arbitrary literals, bounded multiscale candidates/refinement, protected-field edits and new experiment bank for existing HACS Search |
| delivery.py | Opt-in pre-Shield input boundary and separate raw/consumed cue, proposal/execution/purchase and episode-denominator accounting |
| readiness.py | Frozen 100/132-response plans, exact runtime/token attestation, one resident policy, strict call guards, immutable attempt closure and empirical gate join |
| investigation.py | Backend-injected shared active/fixed search; Action initialization and Action/Goal/State final reviews; candidate retained as submitted |
| study.py | Private roles/opaque aliases, budgets/baseline grid, finite-support candidate evaluation, clean dependency/attribution reporting and Markdown exporter |
| simulation.py | New arbitrary-span synthetic discovery scenarios and reuse of existing independent known-rule calibration |
| cli.py | Explicit CPU preparation commands and separately gated model execution; no automatic submit/download/registry writes |

`seek_three_way_train.sh` and `seek_three_way_readiness.sh` are opt-in launchers.
They contain no pinned partition, node or physical GPU index. Training and inference
resources are separate. Existing `agent_eval.sh`, Stage I code and old training
scripts are unchanged.

## Delivery artifacts

Use **`validation/delivery/`** for the final source-bound readiness report, model
match report, proposed campaign/table, synthetic corpora and two-study simulation
smoke. Earlier `validation/`, `validation/final/` and `validation/release/` outputs are intermediate local
CPU preparation snapshots, retained rather than represented as additional studies.
Do not pool them as independent evidence. The final test receipt is
`validation/TEST_RECEIPT.json`.

The synthetic compiler preview has one benign record and four source slots,
producing 17 records in each of C/LQ/LO. Two designated actions differ in each
lexical arm. These are fake CPU examples, not real clean or poison trajectories.
Real training preparation rejects a corpus manifest marked simulated.

## Limits of this delivery

No trained clean/lexical checkpoints, task-grounded corpus review, actual native
FastChat mask verification, real tokenizer/weight verification, utility measurement
or model-execution approval was produced locally. The new full Shield environment
hooks and main-study role/backend integration still need the exact deployed
cluster assets and their parity/tokenization checks; these are not exposed as
ready full-matrix commands. The campaign/grid and backend-injected components
are implemented and CPU-tested, while the first concrete cluster paths are the
compiler/training preparation and readiness workers in `CLUSTER_RUNBOOK.md`.

All new approvals remain false, semantic eta remains unknown, and no authoritative
claim index is allocated. Existing certificates keep their historical interpretation.
A genuine dependency in C is ordinary supported behavior, not a false backdoor
certificate. Legacy SQ/SO are not silently paired with the new C as matched controls.

Native mask boundary follow-up: the cluster's eight-record diagnostic showed
matching native/witness token IDs and a supervised SentencePiece `▁Th` token
covering the final template space plus the first two characters of `Thought`.
The checker now permits exactly this kind of single-space crossing when the
native ADD_COLON_TWO renderer supplies its exact assistant prefix. The token must
still have the correct native label. Role text, undeclared prefixes, broader
crossings, ID mismatches and missing supervision remain failures. Receipts record
each accepted boundary token; trainer and corpus files are unchanged.
The 26 three-way CPU tests pass, including boundary regression checks. A fresh
cluster mask preflight is still required; the previous failed receipt is not
upgraded, and eight short Mind2Web records do not validate WebShop or the full
corpus. All execution approvals remain false.
